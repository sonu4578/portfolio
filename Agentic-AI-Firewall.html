Agentic AI Firewall - Runtime Security for AI Agents

A security layer that sits between an LLM-powered agent and every tool it can call, treating the agent as untrusted by default.

Project Overview

Autonomous AI agents can read files, run shell commands and write to disk, so a single prompt injection or bad decision can cause real damage. The AI Firewall intercepts every action an agent attempts, evaluates it against a declarative policy, risk-scores it, and then allows, blocks, holds it for human approval, or redacts secrets and prompt injections before the agent ever sees them.

A second, independent interception point, a shell wrapper, enforces the same policy for any process running inside its container, whether that is a third-party coding agent or a human at a terminal. Every decision is written to an audit log and surfaced on a live dashboard and Grafana metrics.

Architecture & Design

FirewalledTool proxy — The agent only ever holds a reference to a proxy, never to a real tool implementation, which makes agent-side interception unbypassable.

Firewall engine — A hot-reloadable YAML policy engine, a contextual risk scorer whose score can override policy, a prompt injection detector, and a secret scanner that redacts sensitive values.

Human approval flow — HOLD decisions are queued in Redis and pushed over WebSocket to a React dashboard, where a reviewer approves or rejects the action.

Shell wrapper — Replaces /bin/bash in a sandbox container and posts each command to the same policy engine, covering what the proxy structurally cannot, such as a third-party agent's own terminal commands.

Observability — Decisions are stored in a Postgres audit database and exported as Prometheus metrics (decisions, risk scores, latency, redactions, approval queue depth) with an auto-provisioned Grafana dashboard.

Challenges & Solutions

The main challenge was making enforcement hard to bypass. Rather than trusting the agent to call the firewall, I made the proxy the only handle it has to any tool, and added the shell wrapper as an independent second layer for processes outside the agent. An adversarial test suite tries path traversal, shell metacharacters, embedded prompt injection, approval timeouts, malformed policy rules, the agent modifying its own policy files, and risk escalation under repeated probing, and asserts the firewall holds.

Another challenge was keeping the demo reproducible. A deterministic stub LLM drives named tool-call sequences, so all six demo scenes (allowed action, blocked action, prompt injection, human approval, shell intercept, secret redaction) run end to end without any API key.

Results & Future Enhancements

The proof of concept was built in ten phases, from infrastructure skeleton through metrics, demo scenarios and overhead measurement. The firewall's own added latency is tracked with a p99 target of under 50ms.

Planned production extensions include Open Policy Agent in place of the custom YAML evaluator, Docker exec sandboxing for per-call isolation, a network proxy for LLM API traffic, role-based agent identities, OpenTelemetry, a cryptographically signed audit log, and syscall-level interception to cover in-process calls.
